# SOCKS5-прокси

Учебная реализация части протокола SOCKS5 ([RFC 1928](https://www.ietf.org/rfc/rfc1928.txt)) на Python.
Прокси работает в одном потоке: использует неблокирующие сокеты, селектор и собственный DNS-клиент по UDP.
Внешних зависимостей нет; нужна только стандартная библиотека Python 3.7+.

## Быстрый старт

```bash
cd socks5_proxy
python3 main.py <port> [dns_ip:port]
```

| Аргумент | Обязательный | Описание |
|---|---|---|
| `port` | да | TCP-порт, на котором прокси ждёт клиентов (слушает `0.0.0.0`) |
| `dns_ip:port` | нет | Адрес DNS-резолвера в формате `IPv4:port`, например `1.1.1.1:53` |

Если второй аргумент не указан, прокси ищет системный резолвер и использует UDP-порт `53`:

- Linux/macOS — берётся первая строка `nameserver` с IPv4-адресом из `/etc/resolv.conf`;
- Windows — первый IPv4-адрес в строке `DNS` из вывода `ipconfig /all` (формат может отличаться в локализованных системах);
- если адрес определить не удалось, используется `8.8.8.8:53`, а предупреждение выводится в stderr.

Примеры:

```bash
python3 main.py 1080                 # системный DNS
python3 main.py 1080 1.1.1.1:53      # явный резолвер
```

Остановите прокси сочетанием `Ctrl+C`.

## Что поддерживается

| Возможность | Статус |
|---|---|
| Команда `CONNECT` (`0x01`) | ✅ |
| Команды `BIND`, `UDP ASSOCIATE` | ❌ ответ `REP=0x07` |
| Метод аутентификации `NO AUTHENTICATION REQUIRED` (`0x00`) | ✅ |
| `USERNAME/PASSWORD`, `GSSAPI` | ❌ если `0x00` не предложен — ответ `0xFF` и закрытие |
| Адрес `ATYP=0x01` (IPv4) | ✅ |
| Адрес `ATYP=0x03` (доменное имя) | ✅ с неблокирующимся DNS |
| Адрес `ATYP=0x04` (IPv6) | ❌ ответ `REP=0x08` |
| Двунаправленная передача, half-close | ✅ |

## Структура проекта

```
socks5_proxy/
├── main.py             # точка входа, разбор аргументов командной строки
├── proxy.py            # ядро: цикл селектора и вся логика обработки соединений
├── socks5.py           # разбор/формирование сообщений SOCKS5 (без сокетов)
├── dns_message.py      # сборка DNS-запроса и разбор ответа (A-записи)
├── resolver_config.py  # определение адреса резолвера
├── session.py          # состояние одного клиентского соединения
├── timers.py           # таймеры сессий на куче
├── errors.py           # перевод системных ошибок в коды ответа SOCKS5
└── config.py           # размеры буферов и тайм-ауты
```

Модули `socks5.py`, `dns_message.py`, `timers.py` и `session.py` не зависят друг от друга и от селектора — их можно проверять отдельно.
Вся работа с сокетами находится в `proxy.py`.

### Ответственность модулей

- **`main.py`** — проверяет аргументы, определяет резолвер, создаёт `Proxy` и запускает его.
- **`proxy.py`** — класс `Proxy`: слушающий сокет, UDP-сокет для DNS, селектор, обработчики событий, переходы между состояниями.
- **`socks5.py`** — чистые функции `parse_greeting`, `parse_request`, `greeting_reply`, `build_reply`; константы протокола;
  исключение `ProtocolError` (с кодом ответа или без него, если соединение надо просто закрыть).
- **`dns_message.py`** — `encode_name`, `build_query`, `parse_response`, `decode_hostname`. Поддерживает сжатие имён (указатели `0xC0`)
  с защитой от циклов.
- **`session.py`** — класс `Session` с буферами, флагами и состоянием, а также константы состояний.
- **`timers.py`** — класс `Timers`: куча `(время, номер, сессия, поколение)` и ленивая отмена через счётчик `timer_gen`.
- **`errors.py`** — `rep_for_errno`, набор `CONNECT_IN_PROGRESS`.
- **`config.py`** — все настраиваемые числа в одном месте.

## Как это работает

### Главный цикл

```
пока True:
    timeout = ближайший таймер (или None, если таймеров нет)
    для каждого события из select(timeout):
        слушающий сокет  → принять новые подключения
        UDP-сокет DNS    → обработать ответы резолвера
        сокет клиента    → on_client
        сокет сервера    → on_remote
    обработать сработавшие таймеры
```

Единственный блокирующий вызов — `select()`. Его тайм-аут равен времени до ближайшего таймера.
Если событий и таймеров нет, процесс ждёт в `select()`.

### Состояния сессии

```
GREETING ──(greeting, метод 0x00)──▶ REQUEST ──(CONNECT, IPv4)──────────────▶ CONNECTING ──▶ RELAY
    │                                   │
    │ (нет метода 0x00)                 └──(CONNECT, домен)──▶ RESOLVING ──(адрес получен)──▶ CONNECTING
    ▼                                                              │
 CLOSING  ◀──────────── любая ошибка (ответ с REP ≠ 0) ────────────┘
```

| Состояние | Что происходит | Слушаем клиента на чтение |
|---|---|---|
| `GREETING` | Ждём `VER, NMETHODS, METHODS` | да |
| `REQUEST` | Ждём `VER, CMD, RSV, ATYP, DST.ADDR, DST.PORT` | да |
| `RESOLVING` | Отправлен DNS-запрос, ждём ответ или тайм-аут | нет |
| `CONNECTING` | Идёт неблокирующий `connect()` | нет |
| `RELAY` | Двусторонняя передача данных | да, пока в буфере есть место |
| `CLOSING` | Дописываем клиенту ответ и закрываем | нет |

Если клиент отправил данные сразу после запроса, до ответа прокси сохранит их в ограниченном буфере и передаст серверу после подключения.

### Подписки селектора

После каждого события `Proxy.update` пересчитывает подписки с учётом текущего состояния:

- **Клиент**: `READ` — на этапе рукопожатия или в `RELAY`, если не получен EOF и буфер `клиент → сервер` не полон;
  `WRITE` — только если есть данные для отправки клиенту.
- **Сервер**: `WRITE` — пока идёт `connect()`; в `RELAY` — `READ`, если не получен EOF и буфер `сервер → клиент` не полон,
  `WRITE` — только если есть данные для отправки серверу.

Если сокету не нужны события, его снимают с регистрации. Это не даёт `select()` возвращать его без повода.

## DNS-резолвинг

На старте создаётся один неблокирующийся UDP-сокет, зарегистрированный в селекторе на чтение.

1. Клиент присылает `ATYP=0x03`. Имя декодируется из ASCII (при необходимости UTF-8 преобразуется в IDNA/punycode).
   Если имя — IPv4-литерал, DNS не нужен.
2. Выбирается свободный случайный 16-битный идентификатор; сессия записывается в таблицу `pending[id]`.
3. Через общий UDP-сокет резолверу отправляется запрос A-записи (`RD=1`), и взводится таймер на 3 секунды.
4. При получении ответа проверяется:
   - ответ пришёл с адреса выбранного резолвера;
   - `ID` известен, а сессия ещё ждёт ответ;
   - флаг `QR=1`;
   - в разделе вопросов то же имя, что и в запросе (защита от посторонних и подделанных пакетов).

   Остальные пакеты игнорируются.
5. Прокси получает все A-записи из ответа и по очереди вызывает `connect()`. Если первый адрес недоступен, пробует следующий.
6. Если пришёл `RCODE ≠ 0` (например, NXDOMAIN), записей нет или ответ усечён (`TC=1`) без адреса — это ошибка резолвинга:
   клиенту отправляется `REP=0x04`, соединение закрывается. Повтор запроса по TCP не делается.
7. Если за 3 секунды ответа нет, запрос повторяется. Всего выполняются три попытки: первая и два повтора. После третьей неудачи клиент получает
   `REP=0x04` и соединение закрывается. Остальные клиенты продолжают работать, так как всё ждётся через селектор.

## Передача данных и закрытие соединений

У каждой сессии два буфера: `c2r` (клиент → сервер) и `r2c` (сервер → клиент). Прокси не анализирует данные внутри туннеля, а пересылает их.

- **Память.** Буфер каждого направления ограничен `BUF_SIZE` (64 КБ). Когда он заполнен, прокси приостанавливает чтение (`READ` не запрашивается).
  TCP-окно сжимается, поэтому медленный получатель замедляет отправителя.
  Память на клиента ограничена примерно 128 КБ плюс буфер рукопожатия (4 КБ).
- **Передача данных.** После чтения прокси сразу пытается отправить данные в противоположный сокет, не дожидаясь следующей итерации цикла.
  На сокетах включён `TCP_NODELAY`.
- `WRITE` запрашивается, только когда в соответствующем буфере есть данные.
- **Аккуратное закрытие (half-close).**
  - Получили EOF от клиента → дописываем всё, что накопилось в `c2r`, затем делаем `shutdown(SHUT_WR)` в сторону сервера.
    Читать и пересылать данные от сервера клиенту при этом продолжаем.
  - Аналогично для EOF от сервера.
  - Сессия закрывается, когда получены EOF с обеих сторон и оба буфера пусты.
  - При ошибке сокета (reset, broken pipe) закрываются оба сокета.
- Ошибочные ответы (`CLOSING`) сначала целиком отправляются клиенту, затем выполняется `shutdown(SHUT_WR)` и закрытие.

## Тайм-ауты

Значения тайм-аутов и размера буфера заданы в `config.py`.

| Параметр | Значение | Что ограничивает |
|---|---|---|
| `HANDSHAKE_TIMEOUT` | 30 с | Получение greeting и request; по истечении соединение закрывается |
| `CONNECT_TIMEOUT` | 15 с | Одна попытка TCP `connect()`; затем следующий адрес или `REP=0x04` |
| `DNS_TIMEOUT` | 3 с | Одна попытка DNS-запроса |
| `DNS_ATTEMPTS` | 3 | Число попыток DNS (первая и два повтора) |
| `BUF_SIZE` | 64 КБ | Буфер одного направления |

Таймеры хранятся в куче. При отмене или перезапуске таймера счётчик поколения сессии увеличивается, а устаревшие записи отбрасываются при просмотре кучи.
В состоянии `RELAY` таймеров нет. Тайм-аута простоя тоже нет, поэтому долгие соединения (WebSocket, стриминг) не обрываются.

## Коды ответов SOCKS5

| `REP` | Значение | Когда отправляется |
|---|---|---|
| `0x00` | succeeded | Соединение с сервером установлено (в `BND.ADDR:BND.PORT` — локальный адрес исходящего сокета) |
| `0x01` | general failure | Прочие ошибки `connect()` |
| `0x03` | network unreachable | `ENETUNREACH`, `ENETDOWN` |
| `0x04` | host unreachable | Ошибка/тайм-аут DNS после трёх попыток, неверное имя, `EHOSTUNREACH`, тайм-аут `connect()` |
| `0x05` | connection refused | `ECONNREFUSED` |
| `0x07` | command not supported | Любая команда, кроме `CONNECT` |
| `0x08` | address type not supported | `ATYP=0x04` (IPv6) и неизвестные типы адреса |

Ответ на greeting: `05 00`, если клиент предложил метод `0x00`; иначе `05 FF` и закрытие соединения.
Если версия в первом байте не равна `5`, соединение закрывается без ответа.

## Соответствие требованиям

| Требование | Как выполнено |
|---|---|
| Порт — первый аргумент, DNS `IPv4:port` — второй необязательный | `main.py`, `resolver_config.py` |
| Системный резолвер и порт 53 по умолчанию | `resolver_config.system_resolver()` |
| Только команда `1` | `socks5.parse_request` |
| Согласование метода `0x00` / `0xFF` | `socks5.parse_greeting`, `Proxy.parse_handshake` |
| Неблокирующиеся сокеты, один тред | `selectors.DefaultSelector`, все сокеты в режиме `setblocking(False)` |
| Двунаправленная передача, аккуратное закрытие | флаги `c_eof/r_eof/c_shut/r_shut`, `Proxy.progress` |
| Нет busy waiting | динамические подписки, таймеры через тайм-аут `select()` |
| Ограниченная память на клиента | лимит `BUF_SIZE`, приостановка чтения |
| Скорость | немедленная отправка после чтения, `TCP_NODELAY`, буфер 64 КБ |
| Резолвинг доменов через UDP без блокировок | общий UDP-сокет в селекторе, таблица `pending` |
| Не более трёх попыток DNS, затем `REP=0x04` | `Proxy.on_timeout`, `config.DNS_ATTEMPTS` |
| `TC=1` без адреса — ошибка резолвинга | `dns_message.parse_response` |

## Тестирование

### Через curl

```bash
# IPv4-адрес (ATYP=1)
curl --socks5 127.0.0.1:1080 http://93.184.216.34/

# Доменное имя резолвится прокси (ATYP=3)
curl --socks5-hostname 127.0.0.1:1080 http://example.com/
```

Флаг `--socks5` резолвит имя на стороне curl и передаёт прокси IPv4; `--socks5-hostname` передаёт прокси само имя,
поэтому проверяет DNS-часть.

### Через браузер

Настройте SOCKS5-прокси `127.0.0.1:<port>` и включите «Proxy DNS when using SOCKS v5» (Firefox). Откройте любой богатый контентом сайт
и посмотрите вкладку Network в Developer tools — время загрузки не должно заметно отличаться от работы без прокси.

### Вручную проверить отдельные сценарии

| Сценарий | Ожидаемое поведение |
|---|---|
| Greeting без метода `0x00` (например, `05 01 02`) | ответ `05 FF`, соединение закрыто |
| `CONNECT` на закрытый порт | `REP=0x05` |
| Домен, на который резолвер не отвечает | ответ `REP=0x04` примерно через 9 секунд (3 × 3 с) |
| Несуществующий домен | `REP=0x04` сразу после ответа NXDOMAIN |
| `BIND` / `UDP ASSOCIATE` | `REP=0x07` |
| IPv6-адрес | `REP=0x08` |
| Клиент закрыл запись (`shutdown(SHUT_WR)`) | сервер получает EOF, но ответ ему ещё можно прочитать |
| Передача сотен килобайт в одну сторону | корректно и без роста памяти |

Пока прокси ждёт ответа от «молчащего» DNS, другие клиенты должны продолжать работать.

## Ограничения

- IPv6 (ни как адрес назначения, ни для DNS-резолвера и слушающего сокета) не поддерживается.
- Нет аутентификации; прокси слушает все интерфейсы, поэтому не выставляйте его в недоверенную сеть.
- Нет кеша DNS: каждый новый запрос с доменом порождает запрос к резолверу.
- DNS поверх TCP и EDNS не используются; ответ больше 512 байт (с `TC=1`) считается ошибкой, если в нём не нашлось адреса.
- Нет ограничения на общее число одновременных клиентов (оно ограничено лимитом файловых дескрипторов процесса).
- Нет тайм-аута простоя установленных соединений.
- Определение системного DNS на Windows — по мере возможности (разбор `ipconfig /all`).
