# Змейка по сети (Python, протокол v2)

Многопользовательская «Змейка» по заданию `snakes_task.md` и схеме `proto/snakes.proto`.
Одну игру могут вести программы разных студентов: формат сообщений, таймеры, правила
подтверждений и смены MASTER реализованы по тексту задания.

* графический интерфейс на **tkinter** (входит в стандартную поставку Python);
* сетевая часть — стандартные сокеты, `protobuf` и (необязательно) `psutil`;
* робот не реализован (по заданию не требуется), но игроков типа `ROBOT` от сервера курса приложение принимает.

## Запуск

```bash
python -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python main.py                                    # или: python -m snakes_game
```

Linux: если нет tkinter — `sudo apt install python3-tk`.

Параметры командной строки:

| Параметр | Назначение |
| --- | --- |
| `--server HOST[:PORT]` | сервер курса (по умолчанию `snakes.ippolitov.me:9193`) |
| `--no-server` | не опрашивать сервер, работать только в LAN |
| `--name NAME` | имя игрока по умолчанию |
| `--debug` | подробный лог |

### Как пользоваться

1. **Список игр** обновляется сам: LAN (multicast `239.192.0.4:9193`) и сервер курса показываются
   одним списком, дубликаты склеиваются по `(game_name, endpoint MASTER)`, запись пропадает через 3 с без анонса.
2. **Играть / Смотреть** — присоединиться к выбранной игре (двойной щелчок = «Играть»).
3. **Создать игру…** — имя игры, своё имя, размер поля, запас еды, интервал хода.
   Варианты: вести игру у себя (опционально пригласить робота с сервера) или создать игру на сервере курса.
4. В игре: **W A S D** или стрелки (работает и в русской раскладке). Кнопка
   **«Смотреть / Играть»** снимает/возвращает змейку, оставаясь в сессии; **«Выйти из игры»** — полный выход.
   После гибели змейки вы остаётесь наблюдателем и можете вернуться кнопкой «Играть».
5. Сообщения об ошибках выводятся в строке состояния и не блокируют интерфейс.

## Структура проекта

```
main.py                    запуск без установки
proto/snakes.proto         схема сообщений (из задания)
scripts/gen_proto.sh       пересборка snakes_pb2.py
snakes_game/
  constants.py             константы протокола, таймеры, лимиты
  model.py                 Config, Player, Snake, World, валидация имён/IPv4
  rules.py                 появление змейки, еда, ход, столкновения, очки (чистая логика)
  codec.py                 змейка <-> «ключевые точки», World <-> GameState, проверка снимков
  messages.py              оболочка GameMessage, разбор, проверка размера (<= 1200 байт)
  reliable.py              Outbox (повторы, Ping, лимиты очереди), DedupTable (окно 1024)
  catalog.py               единый список игр с независимым устареванием записей
  session.py               игровая сессия: диспетчеризация, ACK, жизненный цикл
  master_logic.py          логика MASTER: ходы, Join/Steer/Status/Leave, DEPUTY, анонсы, выход
  client_logic.py          логика клиента: подключение, State, failover, переход в MASTER
  node.py                  лобби, запуск/завершение сессий, неизменяемый снимок View для UI
  runner.py                сетевой поток (select) и поток DNS
  net/transport.py         UDP-сокеты: игровой и приёмник multicast
  net/interfaces.py        список IPv4-интерфейсов
  ui/                      tkinter: app, lobby, game, dialogs, theme
tests/                     unittest: правила, кодек, надёжность, сессии, UDP loopback
```

### Слои

```
UI (tkinter, главный поток)  --команды-->  NetworkRunner (поток select)  -->  Node  -->  Session
        ^                                                                       |
        +------------------------ View (неизменяемый снимок) <------------------+
```

* **Потоков ровно три и их число не зависит от игроков, змей, перезапусков и смен MASTER:**
  поток интерфейса, сетевой поток (один `select` по всем сокетам, все таймеры в нём), поток DNS.
* UI и сеть общаются через `queue.Queue` команд и атомарно подменяемый `View` — блокировок нет.
* Все интервалы считаются по `time.monotonic()`.
* На каждую игру создаётся новый UDP-сокет (новый endpoint и новый счётчик `msg_seq`), по завершении закрывается.

## Что реализовано из задания

**Правила.** Дискретный тор; появление змейки в свободном квадрате 5×5 (голова в центре, хвост в случайной
соседней клетке, обе без еды); одновременный ход всех змей; еда с освобождением хвоста (на длине 32 длина не растёт);
столкновения по итоговым положениям (включая обмен голов и погоню за хвостом); очки `N-1` при столкновении `N` голов;
насыщение очков на `INT32_MAX`; смерть → `VIEWING` без смены сетевой роли; целевая еда `food_static + число змей`
пополняется после каждого изменения состояния; лишняя еда не удаляется.

**Протокол.**
* Один `GameMessage` на датаграмму, ≤ 1200 байт; превышение исходящего лимита — ошибка с завершением игры; входящие некорректные/версии ≠ 2 игнорируются.
* ACK копирует `msg_seq` и не расходует счётчик, не попадает в кеш, не подтверждается; несопоставленный ACK игнорируется (но обновляет таймер связи).
* Повтор каждые 100 мс, Ping при 100 мс тишины, предполагаемый отказ при 1000 мс тишины, не более 64 неподтверждённых к соседу (вытесняются только `State`/`Steer`/`Ping`, управляющие операции не теряются).
* Дедупликация по `(game_name, endpoint, msg_seq)` в окне 1024 номеров; повтор получает прежний ответ (в том числе повтор `Leave` после удаления участника); номер ниже окна игнорируется; окно вышедшего endpoint хранится до конца игры; бюджет кеша ограничен (256 endpoint).
* Отправитель прекращает повтор запроса, если к тому же endpoint ушёл номер на ≥1024 больше.
* `Join`: повтор возвращает тот же ID; ACK содержит `receiver_id`, затем приходит `State`; отказ — `ErrorMsg` с `request_seq`, подтверждаемый ACK.
* `Steer` и `PlayerStatusChange` имеют отдельные проверки порядка по `msg_seq`; недопустимый разворот не отменяет предыдущую допустимую команду.
* `state_order` растёт при каждом изменённом состоянии (ход, вход, выход, смена статуса/роли); смена статуса между ходами не двигает змей и расписание ходов; запрос текущего статуса — ACK и повтор `State` без увеличения `state_order`.
* Endpoint отправителя в `GamePlayer` опускается (берётся из UDP-пакета), у остальных — явный.

**Обнаружение.** Два сокета (приёмник multicast и игровой с портом от ОС); подписка на группу на всех IPv4-интерфейсах,
анонсы MASTER через каждый интерфейс; `DiscoverMsg` на сервер курса раз в 1 с из UDP-сокета лобби;
`AnnouncementMsg` MASTER раз в секунду и ответ на `Discover`; создание игры на сервере через `Join` с новым именем
(повтор Join каждые 100 мс, `Discover` каждые 500 мс до получения конфига, общий срок 5 с, снимок `State` до активации буферизуется);
приглашение робота — unicast-анонс на сервер.

**Смена MASTER.**
* MASTER удаляет пропавшего участника и его змейку, назначает нового DEPUTY (из любых NORMAL, включая наблюдателей).
* NORMAL при потере MASTER переключается на последнего известного DEPUTY, перенося неподтверждённые запросы (тот же номер и тело, новые адрес и `receiver_id`); если DEPUTY нет или он тоже недоступен — сессия завершается с ошибкой.
* DEPUTY становится MASTER: продолжает последнюю принятую копию, удаляет прежнего MASTER и его змейку, назначает нового DEPUTY, шлёт `NodeRoleChange(sender_role=MASTER)` и `State` с большим `state_order`.
* Осознанный выход MASTER: `State` → DEPUTY (ждёт ACK), затем `NodeRoleChange(NORMAL→MASTER)` с номером следующего состояния (ждёт ACK); ожидание ограничено 1 с.
* Клиент, ещё не получивший ACK на `Join`, после тишины ищет новый анонс с тем же `game_name` (3 с) и повторяет `Join` новым номером.

## Тесты

```bash
python -m unittest discover -s tests -t . -v
```

* `test_codec_rules` — кодирование змейки (в т.ч. через границу поля), правила хода, столкновения, очки, оценка максимального размера `State` (≤ 1145 байт);
* `test_reliable` — повторы, замена устаревших сообщений, окно дедупликации, перенос запросов при failover, лимит размера;
* `test_session` — на виртуальной сети с управляемыми часами: вход, DEPUTY, отказы при заполненной игре, управление, просмотр/возврат, выход, тайм-ауты, failover, плановая передача роли MASTER, работа при 30% потерь и дублировании пакетов;
* `test_udp_loopback` — два экземпляра на настоящих UDP-сокетах (127.0.0.1): создать игру, найти, присоединиться, играть, уйти в просмотр, выйти.

## Ограничения и замечания

* Приложение проверено автотестами и на loopback; с реальным сервером курса и чужими клиентами в этой среде проверить не удалось — при интеграционной проверке начните с `--debug`.
* Failover и приглашение сервера в вашу игру требуют прямой UDP-связности между участниками (LAN, VPN, публичные адреса); STUN/TURN и hole punching не реализованы (по заданию не требуются).
* Разделение сети на части (partition) и слияние двух MASTER не поддерживаются, как и сказано в задании.
* MASTER игнорирует сообщения зарегистрированных участников без `sender_id` или с `sender_id`, не совпадающим с endpoint (так требует спецификация); если чужая реализация этого не делает, её пакеты будут проигнорированы.
* `pb2`-модуль сгенерирован protoc 4.25 и работает с `protobuf >= 4.25`; для пересборки: `pip install -r requirements-dev.txt && sh scripts/gen_proto.sh`.
